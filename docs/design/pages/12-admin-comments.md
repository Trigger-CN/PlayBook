# 后台评论审核设计

## 1. 页面目标

为管理员提供待审核评论队列、上下文核查、批准、拒绝和删除能力，同时最小化暴露评论者隐私。

- 路由：`/admin/comments`
- 阶段：Phase 8 第一优先级
- 对应需求：`REQ-ADMIN-002/003`、`REQ-INT-007`

## 2. 页面布局设计

### 2.1 桌面端

- 顶部：状态标签（pending/approved/rejected）、目标类型、日期搜索和数量。
- 主体双栏：左侧审核队列，右侧当前评论详情与目标内容上下文。
- 底部/详情操作：批准、拒绝、删除、查看公开目标。
- 批量操作仅在选择后出现，并显示数量及不可逆后果。

列表高密度但保留作者、摘要、目标、时间和风险标记。详情区展示完整评论和有限上下文，不加载整篇文章。

### 2.2 移动端

- 列表与详情分两步导航或全屏抽屉。
- 单条操作优先；批量操作放入明确菜单，避免误触。

## 3. 功能设计

- 默认进入 pending，并在 URL 保留筛选。
- 查看作者昵称、评论正文、提交时间、目标、父评论、基础风险信号。
- 邮箱只显示掩码或不显示；IP/UA hash 默认不展示，仅安全调查时按权限访问。
- 批准后公开可见并失效目标评论缓存。
- 拒绝保留记录用于防垃圾分析，但不公开。
- 删除用于违规或用户请求；需定义软删/硬删和子回复策略。
- 批量批准只用于低风险队列，批量删除要求二次确认。

## 4. 页面状态

- 队列 empty 显示“暂无待审核评论”。
- 处理进行中锁定对应行，其他评论仍可浏览。
- 并发处理返回“已被其他会话处理”，刷新该项。
- 目标已删除时仍可处理评论并标明 orphan。
- 批量部分失败返回逐项结果，不把全部标记成功。

## 5. 数据与权限

读取 `comments` 及目标摘要；更新 `status`、`updated_at`，建议增加 `moderated_at`、`moderated_by`、`moderation_reason`。所有写操作要求管理员并进入审计日志。

## 6. 实现技术要点

- Server Component 按游标分页查询；全文关键字使用受控搜索。
- 状态更新使用 Server Action/RPC，并校验当前状态防止并发覆盖。
- 使用事务更新评论、写审计/活动事件、触发缓存失效。
- 目标摘要通过按类型批量查询，避免 N+1。
- 评论内容始终作为纯文本输出并转义。
- 公开评论缓存 tag：`comments:{targetType}:{targetId}`。

## 7. 可访问性与安全

- 列表选择使用原生 checkbox 和批量栏说明。
- 状态不能只靠颜色。
- 确认对话框初始聚焦取消，并读出评论数。
- 不提供明文 IP、邮箱或 User-Agent；敏感字段访问需额外审计。
- 审核动作防 CSRF，不能用 GET。

## 8. 验收标准

- pending/approved/rejected 筛选和分页正确。
- 批准后公开出现，拒绝后不公开，缓存及时失效。
- 并发和批量部分失败处理明确。
- 目标上下文充分但不泄漏隐私。
- 全流程键盘可操作并有审计记录。
